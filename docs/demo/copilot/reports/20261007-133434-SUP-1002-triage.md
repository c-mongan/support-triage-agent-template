## 🗺️ How It Works (and Where It Breaks)
Beacon signs the exact raw bytes of the body. With global `express.json()`, `req.body` is a parsed object. `JSON.stringify` of it can differ in whitespace, key order or number formatting, so the HMAC differs and the handler returns 401. A rotation alone would not break verification when the new secret is configured, and `Beacon-Signature-Previous` covers the 24h transition.

## 🎯 Root-Cause Assessment
**Assessment:** 🎯 Customer-side body handling. The global `express.json()` from the 14:02 deploy causes verification over a re-serialised body instead of the raw bytes. Rotation is probably a coincidence.
**Confidence:** Likely based on pattern match
**Reasoning:** Timing (first failure 1–2 min after the deploy), continued failure after the secret was updated, documented raw-body requirement, and the match to BEACON-151. It is not "Confirmed by data" because there is no access to delivery payloads or the endpoint's configured secret, and the 13:58 success predates the deploy but its relation to the rotation time is unknown.
**Not explained:** The exact rotation time versus the 13:58 success. A wrong or stale secret in the running process cannot be excluded, although the 14:20 reload still failing argues against it alone. The ticket does not show the rotation time. The retry queue behaviour is not documented in the fixtures.

## Recommended Next Action
